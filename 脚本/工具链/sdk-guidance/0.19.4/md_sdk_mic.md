# Microphone Input

Public API:

- `Builda.audio.requestMicrophone()` / `Builda.mic.start()` / `Builda.mic.read()` / `Builda.mic.stop()` (microphone PCM stream primitives; usually not called directly — by default use the `BuildaMic` built-in component, see "Microphone input" below)

Microphone input (default path: the `BuildaMic` built-in component, zero JS): games that need continuous microphone capture to drive gameplay (volume / blowing / pitch, etc.) should prefer the `BuildaMic` built-in component shipped with the SDK; do not call the L0/L1 primitives directly. Godot integration: ① register the autoload `BuildaMic="*res://addons/builda/mic/builda_mic.gd"` in `project.godot`; ② hook `BuildaMic.start()` onto any tap callback — the built-in state machine handles the "two gestures" automatically (the 1st tap requests permission; when `state` becomes `needs_gesture`, the UI prompts "tap again"; the 2nd tap actually starts capture; a failed recovery after an interruption also returns to `needs_gesture`, reusing the same prompt); ③ read `BuildaMic.volume` (RMS volume) / `BuildaMic.pitch` (Hz, 0 when there is no pitch) every frame to drive gameplay, listen to the `state_changed` signal to update the prompt UI, and when `state == "unavailable"` show a clear **blocking notice** — explain that this game needs the microphone and guide the player to retry or enable it in system settings (calling `BuildaMic.start()` again in the `unavailable` state re-requests permission); never black-screen / freeze / silently do nothing; a no-mic alternative gameplay is an optional bonus, not required; ④ **Packaging**: after the Godot export, copy `addons/builda/mic/web/` as-is into the export directory before zipping — the analysis worker must ship with the game bundle; `builda dev` locally falls back to the project directory automatically, so do not be fooled by "it works locally"; a production bundle missing the file fails with `WORKER_LOAD_FAILED`; ⑤ to change the algorithm / add features, only edit `addons/builda/mic/web/builda-mic-worker.js` (heavy DSP belongs in this Worker; the object fields the worker sends via `postMessage` appear as-is in `BuildaMic.features`) — this directory is owned by the project, `sdk install` upgrades do not overwrite it, and deleting the directory and reinstalling restores the default analyzer. Data-plane note: PCM never enters GDScript; only a few dozen bytes of feature JSON cross the bridge per frame.

Unity integration (the `Builda.BuildaMic` component, isomorphic to the Godot version): ① attach the `BuildaMic` component (`Assets/Builda/Runtime/BuildaMic.cs`) to a persistent scene object; ② call `StartMic()` in a tap callback — the same two-gesture state machine (when `State` becomes `NeedsGesture`, prompt "tap again"; subscribe to the `StateChanged` event to update the prompt UI; the blocking notice for the `Unavailable` state follows the same rules as Godot); ③ read `Volume` / `Pitch` (or the `Features` dictionary) every frame to drive gameplay, and call `StopMic()` when not in use; ④ **Zero manual packaging**: the analysis worker lives in `Assets/StreamingAssets/builda-mic/`, and the Unity WebGL build copies it into the output as-is automatically (simpler than Godot here, no manual copy needed); ⑤ to change the algorithm / add features, only edit `Assets/StreamingAssets/builda-mic/builda-mic-worker.js` — this directory is owned by the project, `sdk install` upgrades do not overwrite it, and deleting the directory and reinstalling restores the default analyzer. HTML5 projects have no built-in component; build your own following the L0/L1 direct flow below (the `samples` from `read()` can be transferred directly to your own Worker).

Advanced (L0/L1 direct calls, usually unnecessary): the standard flow is **two gestures** — in the 1st tap callback (e.g. an "Enable voice control" button) call `Builda.audio.requestMicrophone()` (Godot side `builda.audio_request_microphone()`) to request permission: `available: false` means the user denied it or the device has no mic; the game just shows a clear blocking notice (explain that the microphone is needed and that the player can retry; a no-mic alternative gameplay is optional); after the permission result comes back, **do not call `mic.start()` directly** — the permission result callback is not a gesture context (Godot's `sdk_result` signal is dispatched via per-frame polling and is inherently detached from the gesture; the "Allow" the player taps on the browser/system permission dialog does not reach the page either), so if written in the result callback, `AudioContext` will inevitably be blocked by the autoplay policy and cannot recover. The correct approach: stay on a "tap again to start" prompt screen, and in the 2nd tap callback call `Builda.mic.start()` (`builda.mic_start()`, idempotent and re-entrant; concurrent/repeated calls are deduplicated in flight by the SDK with merged results, and never return a transient `BUSY`). Then each frame call `Builda.mic.read()` to synchronously pull mono float32 PCM (Godot side `builda.mic_read()` returns a Dictionary directly, and `samples` is restored to a `PackedFloat32Array` with `builda.mic_samples()`), and call `Builda.mic.stop()` when not in use. The SDK only provides raw PCM and does no feature analysis: put pitch/volume extraction in the CP's own Web Worker (on the JS side the `samples` from `read()` can be transferred directly with `postMessage`); **do not** run heavy DSP in GDScript or on the main thread — under single-threaded Godot exports it competes with the engine for frame budget. `dropped > 0` returned by `read()` means pulling was too slow and data was overwritten (usually harmless for real-time control; do not treat it as a continuous stream for recording); `state == "interrupted"` means capture was interrupted (incoming call / backgrounded); the SDK rebuilds automatically when returning to the foreground, and for long interruptions guide the player to tap and call `start()` again (sharing the same "waiting for gesture" prompt as the first start is fine). **PCM may only be analyzed locally in real time; never retain or upload recordings — violations are treated as review incidents.** The manifest permission declaration (`permissions`) for the microphone will be added after the platform side ships it; for now do not add that field to `builda.publish.json`.

Microphone test cases (in the `builda dev` shell; go through each one before release): ① Normal path — after two gestures, make sound and confirm the features drive gameplay; ② Tap "Deny mic" and reload — confirm the game shows an explicit "microphone required" blocking notice (rather than a black screen, freezing, or repeatedly prompting for permission), and that the retry entry in the notice can request permission again; if the game has a no-mic alternative gameplay (optional), verify it too; ③ While the game is running, tap "Microphone interruption" — confirm the game gives feedback for the interrupted state (pause/notice), then tap the toggle again to turn it off — confirm gameplay continues after automatic recovery; ④ Test voice-control sensitivity with BGM on (BGM crosstalk is always present in the PCM, so thresholds must be tuned under the real mix); ⑤ For games using BuildaMic: confirm the production zip contains the analysis worker (Godot: `addons/builda/mic/web/`, must be manually copied into the export directory; Unity: `StreamingAssets/builda-mic/`, included automatically by the build) — local dev has a fallback, so a missing worker in the zip only blows up as `WORKER_LOAD_FAILED` on real devices.
