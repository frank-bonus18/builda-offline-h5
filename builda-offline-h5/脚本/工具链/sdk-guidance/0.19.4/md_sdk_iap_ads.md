# Payments and Rewarded Ads

Public API:

- `Builda.iap.showPayPanel(saleId, { grantBy })` / `Builda.iap.claim(orderId)` / `Builda.iap.getPendingOrderIds()` (in-app purchase (IAP): no automatic claim, see the payment/ad rules below)
- `Builda.pay.showPayPanel(saleId)` (**legacy**: the host claims automatically; kept only for existing live games; new code must not use it)
- `Builda.ad.showRewardAd(posId)` (`posId` is named freely by the game and used only for statistics; **no ad slot application needed**, see the payment/ad rules below)

Payments and ads must go through the Builda SDK; do not call the underlying App bridge directly from game business code:

- The payment entry is `Builda.iap.showPayPanel(saleId, { grantBy })` (Godot side `builda.iap_show_pay_panel(sale_id, grant_by)`, Unity `IapShowPayPanel(saleId, grantBy, cb)`). `saleId` is the `payId` declared in `payPoints` of the current game's draft manifest. For `grantBy`, **pass explicitly** the granter this code path intends to use (`"client"` / `"room"`): the host passes it through with the order for discrepancy diagnostics; the declaration does not override the granter frozen into the order from the published configuration, nor does it guarantee order creation is rejected on mismatch. Actual granting must branch on the order's `grantBy` in the response; when omitted, the host uses the price list declaration, and recovering pending orders still follows the old order's frozen value. Product configuration reads and order creation/query/retry are all done by the App host directly against the platform server and are not exposed to the game; the game must not build its own order requests. `Builda.pay.showPayPanel` is **legacy** (the host claims automatically before responding; client orders go straight to Delivered, cannot be re-granted, and it cannot be used with `grantBy=room`); it is kept only for existing live games, and new code must not use it; when migrating an old game to `iap`, you must add both the claim and the recover-pending-orders logic.
- Games with in-app purchases declare `payPoints` in `builda.publish.json`. Each point must have `payId` / `payName` / `price`, along with the granter `grantBy`: only `"client"` or `"room"` is allowed (one `payId` can only have one granter). Omitting `grantBy` or the empty string `""` equals `"client"` (the client grants idempotently after `showPayPanel` succeeds). Room granting must explicitly set `"grantBy":"room"`, then hand the `orderId` to Room `doOrder`. `null`, other types, whitespace and invalid enum values are all illegal. Note: without in-app purchases you must omit `payPoints` entirely; do not write an empty array `[]`. Ordinary reskins or gameplay updates do not change `payPoints`; edit it only when adding, repricing, changing the granter of, or removing a pay point.
- `price` is an integer in the platform virtual currency **G coins** (not RMB cents). Pricing rules: the minimum payment amount is 100 G coins (1 RMB is worth about 10000 G coins); please design price tiers as integer multiples of 100 G coins where possible (e.g. 100, 300, 1000). Omitting the `payPoints` field = leave the platform's existing price list unchanged (so a pure bundle update will not accidentally clear pay points).
- **There is currently no way to "remove all pay points"**: deleting `payPoints` entirely only means "no change" and does not clear them. To remove them, contact the platform; do not send an empty array trying to clear them.
- `iap.showPayPanel` returns `{success, orderId, grantBy}`: `success == true` **only means the payment succeeded**; the order stays in Paid and granting is not complete; `success == false` means cancelled or failed, so do not grant. `grantBy` is the granter the host froze with this order; **it is authoritative** — do not infer it from the current price list. Grant according to `grantBy`: for `client` (also when omitted/`""`) the client grants idempotently by `orderId`, and **after granting you must call `Builda.iap.claim(orderId)`** (Godot `iap_claim`, Unity `IapClaim`; Paid→Delivered, idempotent, repeated calls replay success; otherwise the order stays in the undelivered list forever); for `room`, hand the `orderId` to Room `doOrder` → `allowed` → `fulfill`, and **the client must not grant and must not claim**.
- `Builda.iap.getPendingOrderIds()` (Godot `iap_get_pending_order_ids`, Unity `IapGetPendingOrderIds`) is read-only and returns `{orderIds}`, used to show the current undelivered (Paid but not claimed) orders. The list has **no** `payId` / `grantBy`. Granting responsibility follows what was frozen **at the time of ordering**; you cannot infer it for old orders from the current price list, nor guess it from a bare `orderId`. Existing host capabilities: the `iap.showPayPanel` response at payment time carries that order's frozen `grantBy`, and the game just persists orderId→grantBy; the pending query only has `orderId`; only `allowed` from Room `doOrder` carries a trusted `payId`; when the granter is unknown, **do not assume client-side granting**. Only hand `orderId` to Room for orders confirmed as `grantBy=room`; only grant idempotently on the client for orders confirmed as `grantBy=client`. Do not poll, do not call it immediately on entering the game, and do not build your own HTTP requests.
- `Builda.ad.showRewardAd(posId)` is the rewarded video ad entry for granting in-game items. `posId` is the game's **custom** ad placement statistics identifier: any string (e.g. `revive`, `double_reward`), used only to distinguish different ad trigger points in the game for statistics; it is not a platform-assigned ad slot ID, **no application needed**, and it does not need to be declared in the manifest like `saleId`/`rankId`. `success == true` means the ad was watched validly, and the game grants in-game item rewards per its own design; `success == false` means failure, closed midway, or the host has no ads integrated, so do not grant. The game must not call any ad verification endpoint.
- In a browser or without the Builda App host, payments/ads return `HOST_UNAVAILABLE`; never fake a successful purchase or a successfully watched ad.
