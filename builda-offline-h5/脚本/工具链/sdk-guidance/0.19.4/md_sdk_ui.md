# Safe Area, Floating Button, Text Input and Localization

Public API:

- `Builda.runtime.safeArea()` (safe area insets on four sides, notch adaptation, see "Notch / safe area adaptation" below)
- `Builda.runtime.capsuleMenuRect()` (platform floating button rect, for avoidance/alignment, see "Notch / safe area adaptation" below)
- `Builda.runtime.language()` (current language, returned synchronously, see "Localization" below)
- `Builda.input.showInputPanel(opts)` (opens the platform input box + keyboard for text input, see "Text input" below)

Notch / safe area adaptation: on phones the game view fills the full screen by default, including the notch/punch-hole and the iOS bottom home-indicator area. The background can stay full-screen as usual, but key HUD, buttons and other interactive UI must avoid these areas — call `Builda.runtime.safeArea()` (Godot side `runtime_safe_area()`) to get the safe area insets on four sides `{top, right, bottom, left}`, in CSS pixels, all 0 on devices without a notch; on the JS side it is a synchronous method that returns a bare object directly (like `assets.url`, no await needed, no `ok` wrapper), so you can safely fetch it fresh in every resize callback. When the game viewport resolution differs from the browser window, first convert proportionally (inset × viewport width ÷ window CSS width) before applying it to UI margins. For local verification, add the `--safearea` flag to inject mock values, e.g. `builda dev --web build/web --safearea 44,0,34,0` (top, right, bottom, left: simulating a 44 top notch and a 34 bottom home indicator), and confirm in the browser that the UI avoids the corresponding edges.

Platform floating button avoidance: the platform's general settings / pause-exit entry is a floating button overlaid on the top-right corner of the game view (similar to the capsule button in WeChat mini games). Call `Builda.runtime.capsuleMenuRect()` (Godot side `runtime_capsule_menu_rect()`, synchronous bare return) to get its rect `{top, right, width, height}` — `top`/`right` are the distances from the viewport's top/right edges, with the same inset semantics as `safeArea` (CSS pixels); `width/height` of 0 means there is currently no floating button, and no avoidance is needed. The game must not place clickable UI inside this rect; your own top buttons can use its `top`/`height` to align and line up to its left, visually like a single system bar. On real devices this floating button strip = an 80×32 settings/exit capsule on the right + 8 spacing + a 32×32 round chat button (opens the host chat page; the game must not build its own chat UI) + 8 spacing + a leftmost 32×32 multiplayer members button (only shown inside a multiplayer room; opens the host room members page; the game must not build its own), and the rect always covers the whole 160×32 strip regardless of whether the player is in a room, so laying it out once at game start is enough. The local mock returns `top = safeArea.top + 6, right: 10, 160×32` (without `--safearea` that is `{top:6, right:10, width:160, height:32}`); once `builda dev` starts the server you can verify the avoidance directly in the browser.

Text input: in a phone WebView, a self-drawn input box in Godot Web cannot get the system IME (no pinyin candidates, cursor or selection), so for naming, entering room numbers and any other text input always call `Builda.input.showInputPanel({placeholder, defaultValue, maxLength})` (Godot side `builda.input_show_panel(placeholder, default_value, max_length)`) — the platform pops up a native "input box + keyboard" (no title bar); confirm returns `{confirmed: true, text}`, cancel returns `confirmed: false`. The returned `text` has already passed the platform's sensitive-word review and length truncation; the game uses it directly and must not submit it for review again. For prefill scenarios such as renaming, pass the current value as `defaultValue`. Only one panel is allowed at a time; calling again while it is still open returns `BUSY`; **do not** draw your own text box and listen for keyboard events. In local `builda dev`, the mock pops up an input bar docked at the bottom and focuses a real input to bring up the system keyboard, equivalent to real-device behavior.

Localization: if the game is localized, use `Builda.runtime.language()` (Godot side `builda.runtime_language()`) to get the current language; it returns a BCP 47 hyphenated string, is a synchronous method that returns a bare string directly (no await needed, no `ok` wrapper), falls back to `en` when unavailable, and never returns an empty string. The platform only provides **bare language codes** (`zh`, `en`, with no regional variants; `zh-CN` never appears), with the sole exception of Spanish as `es-419` — do not design Simplified/Traditional branches or region-specific copy. The Builda App currently supports 11 languages: `en` (English), `zh` (Simplified Chinese), `ja` (Japanese), `es-419` (Latin American Spanish), `fr` (French), `id` (Indonesian), `pt` (Brazilian Portuguese), `ru` (Russian), `th` (Thai), `tr` (Turkish), `vi` (Vietnamese). A game does not have to translate all of them; pick the languages that fit the game and let the rest use the fallback below. More languages may be added later, so never treat this list as closed: an unknown code must also reach the fallback. When matching your own language packs, still use the three-level fallback "exact match → language-prefix downgrade (e.g. `es-419` → `es`) → game default language"; do not only do an equality comparison. Reading it once at startup to decide which copy set to load is enough; the host supports switching language at runtime, and rereading at points such as scene switches keeps up with changes, with no polling needed. In local `builda dev`, the mock normalizes the browser's `navigator.language` to the same granularity (e.g. `zh-CN` → `zh`, `es-MX` → `es-419`); to test a specific language, add a parameter such as `builda_mock_lang=es-419` to the game URL to override it. When the user wants localization or hits text rendering as boxes (tofu) on Web, first read the full practice guide: `./md_godot_i18n.md` (embedded copy tables, font subsetting, missing-glyph filtering for open-set text such as leaderboard player names, layout of long Japanese/Russian copy). Font rules differ by engine: Godot Web exports (wasm self-rendering) have no system font fallback, so fonts are handled by the game and shipped in the bundle — never pack full CJK fonts directly into the bundle (subset them with fontTools), and never load fonts from any external CDN (the platform provides no shared fonts, and under COEP external links are blocked, causing a white screen); Unity WebGL is the same (neither TMP nor legacy Font has system fallback; fonts are embedded and subset; for TMP/legacy choice, i18n copy tables and open-set text missing-glyph filtering see chapter 5 of `./md_unity_webgl.md` — **the editor Game view has system font fallback, so font acceptance must be done in a Web build**); games rendered with HTML5 (pixi/phaser/canvas) are the opposite: **prefer system fonts directly** (see "HTML5 packaging"), and do not copy Godot's font subsetting process.
