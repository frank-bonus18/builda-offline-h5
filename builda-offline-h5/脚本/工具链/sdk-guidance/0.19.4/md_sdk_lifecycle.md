# Lifecycle, Foreground/Background, Keep Screen On and Host Version

Public API:

- `Builda.runtime.ready()` (**must be called at the very start of the game**: the first thing in the entry script/first scene; do not put it after assets finish loading; if the host does not receive ready within 30 seconds of page load it force-closes the game, so make sure every path reaches it)
- `Builda.runtime.quit()` (may be left uncalled if there is no active-exit scenario: the platform's built-in capsule menu provides an exit entry; calling it brings up the platform's generic pause/exit page, see "Platform generic settings/exit page" below)
- `Builda.runtime.setKeepScreenOn(enabled)` (keep-screen-on toggle for idle/incremental gameplay, **requires App ≥ 1.84.0**, see "Keep screen on" below)
- `Builda.runtime.appVersionAtLeast(target)` / `Builda.runtime.appVersion()` (host version detection, returns synchronously, see "Host version detection" below)
- `Builda.events.on(name, handler)` / `off(name, handler?)` (subscription-style callbacks for events the platform pushes to the game. `appVisibility`: payload `{visible, source}`, `visible=false` = App minimized/backgrounded/screen locked, `true` = back to foreground; `pausePanel`: payload `{visible}`, `true` when the host "Paused" (已暂停) panel pops up / `false` when it closes without exiting. Godot side `builda.app_visibility_changed(visible, source)` / `pause_panel_changed(visible)` signals, Unity side `BuildaSDK.AppVisibilityChanged` / `PausePanelChanged` events. See "App foreground/background and pause panel callbacks" below)

App foreground/background and pause panel callbacks: when the player sends the App to the background, minimizes it or locks the screen, the game should pause (gameplay, timers, BGM, non-essential network writes) and resume when back in the foreground. Subscribe with `Builda.events.on("appVisibility", ({visible, source}) => ...)` (Godot side connect the `builda.app_visibility_changed(visible, source)` signal; Unity side `BuildaSDK.AppVisibilityChanged += (visible, source) => {}`): `visible=false` pauses, `true` resumes. The SDK already normalizes host pushes (`source:"host"`) and the WebView `visibilitychange` fallback (`source:"browser"`) and deduplicates by state, so the game must not listen to `document.visibilitychange` or the host `onEvent` itself, nor branch logic on `source`. It fires only on state changes and does not replay the current state on subscription. `on` returns an unsubscribe function. Games with timing/match logic (runners, timed challenges, multiplayer) must integrate it; pure turn-based games are also advised to integrate it to pause BGM. The local `builda dev` test shell has a "Background" button (切后台 in a Chinese browser) for verification (simulating a host push); switching browser tabs exercises the fallback path. The same API also has the `pausePanel` event: when the player taps the platform capsule ✕ or the game calls `runtime.quit()` and the host "Paused" (已暂停) panel pops up, it delivers `{visible:true}`; when "Continue game" (继续游戏) closes it, it delivers `{visible:false}` (an actual exit does not fire it). While the panel is up, the host only pauses BGM and sound effects and game logic keeps running, so games with timing/match logic must subscribe to it to pause gameplay (Godot side `builda.pause_panel_changed(visible)`, Unity side `BuildaSDK.PausePanelChanged`). The two event groups are orthogonal; handle them as "pause if either says pause, resume only when all have resumed", and do not treat pausePanel as a subset of appVisibility. In the local test shell, tap the capsule button to verify.

Merge pause state: track appVisible and pausePanelVisible, and use `!appVisible || pausePanelVisible` to decide pausing in one place. Do not resume directly in each of the two callbacks, otherwise returning to the foreground while the pause panel is still open will wrongly resume the game. The Godot/Unity examples already use the merged state.

Platform generic settings/exit page: the Builda platform provides generic settings and pause/exit entries and pages on top of the game, including music and sound-effect toggles. Therefore the game must **not build its own music/sound-effect toggles** (not in a settings page either); muting is managed uniformly by the platform — the player's choice there is a **persistent cross-session** preference, while `Builda.audio.setMuted()` is the game's **temporary** request (ducking background audio during a cutscene and the like); the platform combines the two: if either side requests mute, it is muted. So the semantics of `setMuted(false)` are "I withdraw my own mute request", **not** "turn the sound on" — if the player turned the music off, nothing the game calls will make it play; this is by design, do not treat it as a bug to work around. Remember to withdraw temporary ducking with `setMuted(false)` when done; do not keep it pressed down; on game exit you need not handle it, as the platform clears it along with the session. An exit button is likewise unnecessary — the capsule menu already provides an exit entry, and when the game has no active-exit scenario `Builda.runtime.quit()` may be left uncalled; if called, it does not close the game directly but brings up the platform's generic pause/exit page, where the player decides whether to stay or leave.

Keep screen on (**minimum host version: App 1.84.0**): for idle, incremental, long-animation or dashboard-style gameplay where the player does not touch the screen for a long time but is still watching, use `Builda.runtime.setKeepScreenOn(true)` to prevent the system from auto-sleeping the screen, and `setKeepScreenOn(false)` to restore when no longer needed (Godot side `builda.runtime_set_keep_screen_on(true)`, Unity side `BuildaSDK.RuntimeSetKeepScreenOn(true, cb)`). The returned `data.enabled` is the **actual effective state**, not an echo of the argument: it is `false` when the host does not support the capability or the system refuses, and the game can use it to prompt the player "please do not lock the screen"; do not assume the call always takes effect. Hosts older than 1.84.0 do not recognize the command and reply with an `UNSUPPORTED_CMD` error envelope; just treat it as "not supported" — there is **no need** to probe with `appVersionAtLeast("1.84.0")` first; the return value of a single call is enough.

**No need to turn it off before exiting**: keep-screen-on is scoped to the current game session; the host resets it on its own when leaving the game page, and the game page may be destroyed directly without any chance to run cleanup. Likewise, backgrounding is taken over by the system and on returning to the foreground the host automatically restores the game's last setting, so do not write re-apply logic either. Call it only when the gameplay state really changes (e.g. on when entering the idle screen, off when leaving it); do not call it repeatedly every frame or on a timer. The mock in local `builda dev` approximates it with the browser Screen Wake Lock API and returns `enabled:false` when unsupported, which is handy for verifying the degraded branch. The browser side has two hard prerequisites: a **secure context** (https or localhost) and **the page being currently visible** — when `document.visibilityState` is not `"visible"` the browser always refuses with `NotAllowedError: The requesting page is not visible`, for top-level pages and iframes alike. So **this capability cannot be verified in headless browsers, background tabs or minimized windows**, and `enabled:false` from automated tests does not mean the host lacks support. To verify, use a visible foreground window; on real devices the host implements it natively and is not subject to these restrictions.

Host version detection: to determine whether the host Builda App is new enough to support a capability, **always use `Builda.runtime.appVersionAtLeast("1.84.0")`** (Godot side `builda.runtime_app_version_at_least("1.84.0")`, Unity side `BuildaSDK.RuntimeAppVersionAtLeast("1.84.0")`). The synchronous method returns `true`/`false` directly, needs no await and has no `ok` wrapper; **do not fetch the version string and compare it yourself** — the SDK internally compares numbers segment by segment per semantic versioning, and handwritten string comparison gets cross-digit versions like `"1.9.0"` vs `"1.10.0"` backwards. Other relations are composed from it: less-than is `!atLeast(x)`, a range is `atLeast(a) && !atLeast(b)`.

The platform provides the real version number starting from App **1.84.0**; older Apps do not provide it, and the SDK uniformly treats them as **`1.83.0`** (the last version that does not provide the value), which is also the default of the local `builda dev` mock — so the game need not distinguish "old host" from "no host"; `appVersionAtLeast` returns `false` in both cases, and both should be treated as "not supported" and take the degraded branch. To test the other branch, add `builda_mock_app_version=1.84.0` to the game URL to override the mock's return value.

`Builda.runtime.appVersion()` returns the raw version number string (never an empty string); use it only when you need to display or report the raw value, never for branching decisions. Note this value is **not** the game's own version (that is `Builda.runtime.bundleVersion`), and do not put it into saves.
