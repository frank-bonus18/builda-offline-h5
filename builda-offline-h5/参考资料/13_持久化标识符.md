# Pre-Release Audit of Persistent Identifiers

This page constrains privateKV keys, payId, rankId and identifiers derived from them; it does not constrain Player Data query keys.
Player Data uses the raw field names defined by the game server; do not rename or migrate them on your own; their key contract is in
`https://ai.builda.game/game-sdk/releases/0.19.4/md_sdk_player.md`.

Starting from Agent/SDK `0.3.1`, the accepted contract for privateKV keys is `^[A-Za-z0-9_:-]{1,64}$`; the accepted contract for `payId` and `rankId` is `^[A-Za-z0-9_-]{1,64}$`. The project SDK, runtime SDK, Builda draft backend and the cysj cloud save write service must stay consistent.

Illegal privateKV keys containing `.`, `+`, `/`, spaces, `$`, non-ASCII, etc. are deterministically rejected; old data is not automatically deleted. The colon `:` is a compatibility character for privateKV: existing keys such as `save:main` and `save:main:slot:0` can still be read, written and deleted, and you must not require migration or block a draft solely because of colons. Do not misjudge a genuine invalid-argument failure as a network error and retry it.

## Audit Scope

Do not only fix the `pay_order.*` that currently appears in the logs. You must inventory all identifiers the game creates, concatenates or persists:

- Single and batch keys of `Builda.privateKV.*`, Godot `private_kv_*`, Unity `Kv*`.
- `payPoints[].payId` in `builda.publish.json`, and the values passed to `showPayPanel(saleId)`.
- `rankBoards[].rankId` in `builda.publish.json`, and the values used for leaderboard submission and queries.
- Keys the game derives itself, such as payment order idempotency records, save slots, player progress and leaderboard caches.
- Wrapper functions around the above APIs, and array or dictionary keys generated at runtime in `getMany/setMany/removeMany`.
- Player data persistence that bypasses privateKV, such as `localStorage`, IndexedDB, Cookie, Godot `user://`.

Platform-returned values such as `orderId`, `transId`, player ID and game ID are opaque. Do not assume they conform to the key rules, and do not concatenate them as-is into privateKV keys.

## Safe Subset for New Code

privateKV keys, `payId` and `rankId` added or modified by the developer agent must only use:

```text
^[A-Za-z0-9_-]{1,64}$
```

That is, ASCII letters, digits, `_`, `-`. New code must not use `.`, spaces, `$`, `:`, `+`, `/`, backslashes, non-ASCII characters or other punctuation. privateKV additionally accepts `:` for compatibility with live saves, but new code should still prefer `_` and `-`; do not ask the server to allow `.` for the game.

When existing identifiers are found outside the recommended subset for new code:

1. If a privateKV key only additionally uses `:`, it still conforms to the accepted contract; do not migrate it and do not block release.
2. If it contains genuinely illegal characters such as `. + /`, spaces, `$` or non-ASCII, clearly tell the user the impact after upgrading, then design a migration plan.
3. Old privateKV data is kept by default; never automatically call remove to delete it; any cleanup is a separate irreversible operation and must again obtain the user's explicit authorization.
4. Changing a `payId` changes the product mapping; changing a `rankId` is equivalent to a new board and may lose historical scores. Before doing so you must explain the impact to the user and obtain explicit confirmation.

## Payment Order Keys

The `orderId` from the payment success response must first be stably hashed before deriving the idempotency key. Fixed algorithm:

```text
pay_order_<first 48 lowercase hex chars of sha256(orderId UTF-8)>
```

The final key is 58 bytes. Do not use `pay_order.<hash>`, `pay_order:<hash>` or `pay_order_<raw-order-id>`, and do not let different games choose their own truncation length.

Dynamic identifiers in new code should converge into a small number of constructor functions: a fixed ASCII prefix, stable hashing or safe encoding of external input, and after concatenation validation against the new-code safe subset `^[A-Za-z0-9_-]{1,64}$`. This is a convention for newly added code and does not change privateKV's accepted contract for existing colon keys. When validation fails, stop this persistence and log the purpose and error code; logs must not contain tokens or full sensitive values.

## Development Checks

For changes involving privateKV, payments or leaderboards, the developer agent should trace aliases, wrapper functions, template strings, format strings, multi-line arguments and dynamic containers to confirm the final generated keys/IDs conform to this page's constraints. When adding dynamic identifiers, record their format and purpose; existing `privateKV key`, `payId` and `rankId` stay unchanged by default, and if migration is truly needed, first explain the data impact to the user.

`create-draft` / `update-draft` validate structured fields in the manifest such as `payPoints` and `rankBoards`; the SDK and backend continue to validate the key/ID format in actual requests. Source-code identifier design is a development responsibility and does not additionally block upload or draft submission.

## Batches, Errors and Retries

- If any key in `setMany` is illegal, the whole batch is rejected; you cannot assume the legal items in the same batch have been written.
- `BAD_KEY`, server `200452`, explicit invalid-argument errors, quota or value-too-large errors are deterministic failures: stop retrying immediately, and fix the code or data before trying again.
- Transient errors such as network timeouts or the host being temporarily unavailable may only be retried with capped exponential backoff, and only when idempotent; once the cap is reached, stop and surface the failure to the upper layer.
- Never retry privateKV writes every frame, every second, or in an infinite loop.

## Minimum Test Matrix

- Each final key format completes at least save, read, and the corresponding delete or business operation.
- Payment order records and a regular save (e.g. `demo_profile_v1`) are written in the same batch and read in the same batch successfully.
- After restarting or re-entering the game, both the order idempotency records and the regular save can be restored.
- Repeated callbacks for the same `orderId` do not grant rewards twice, and different `orderId`s do not collide.
- Illegal characters get a deterministic failure without retry; the retry count and backoff for transient errors have explicit caps.
