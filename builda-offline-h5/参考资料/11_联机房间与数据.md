<h3 id="玩家数据">玩家数据</h3>
<p><strong>玩家数据（Player Data）</strong> 按游戏 + 玩家保存、跨房间保留，权威读写与支付发货由 Room 负责。
基础 SDK 的 <code>Builda.playerData.getMany</code> / <code>listKeys</code> 可在已发布游戏联网登录后、不进房时只读观察本人数据；草稿试玩不支持。观察结果可能滞后，不能据此扣款或发奖。<code>privateKV</code> 是另一套私域存档。TypeScript Room 使用 <code>cloudEnqueue</code> / <code>cloudRead*</code> / <code>cloudFlush</code> /
<code>cloudLoadSnapshot</code>，Rust Room 使用对应的 <code>cloud_state_api</code>。</p>
<ul>
<li><code>cloudEnqueue</code> 成功只表示写入已排队；需要确认这批写入已生效时，调用 <code>cloudFlush</code> 等待 applied。</li>
<li>已经持有的快照不会自动刷新；applied 后重新加载快照，或玩家重新进房，才能读到新值。</li>
<li><code>builda.</code> 开头的键由平台保留，游戏不要读写。</li>
</ul>
<p>语义或故障请反馈玩家数据维护方，不要当成客户端 SDK 问题。</p>
<h3 id="游戏数据">游戏数据</h3>
<p>Game Data 按游戏共享，适合跨 Room 使用的对象、有序索引和计数器；它与按玩家保存的玩家数据不同。TypeScript Room 使用 <code>this.gameData</code>，Rust Room 使用 <code>context.game_data()</code>。同步调用返回 <code>Operation</code>；异步调用可在受管任务中等待。具体示例和读写限制见安装后的 Online Skill。</p>
<p>对象读取可能受缓存影响，正确性应使用条件更新；本地 Mock 默认将已完成的数据保存到本地文件，可跨进程重启继续测试；不恢复 Room 连接、进行中的操作或未知结果恢复句柄，不能代替线上验收。消息队列当前暂停，返回 <code>unsupported_capability</code> / <code>game_data_message_queue_disabled</code>，不要自动重试。</p>
<h3 id="支付发货">支付发货</h3>
<p>内购付费点在 <code>builda.publish.json</code> 的 <code>payPoints</code> 里用 <code>grantBy</code> 声明发货方：</p>
<ul>
<li><code>&quot;client&quot;</code>（省略或空串同义）：客户端自己幂等发货后调用 <code>Builda.iap.claim(orderId)</code>，Room 不参与。</li>
<li><code>&quot;room&quot;</code>：必须显式声明。客户端支付成功后把 <code>orderId</code> 通过 Match 消息发给 Room，由 Room 发货；客户端不发货，也不 claim。</li>
</ul>
<p>Room 发货流程：</p>
<ol>
<li>收到 <code>orderId</code> 后调用 <code>doOrder</code> / <code>do_order</code>，结果在后续 tick 进入回调，不要阻塞等待。</li>
<li>只在结果为 <code>allowed</code> 时，在同一回调内用 <code>fulfill</code> 给该玩家写玩家数据（例如增加金币）。商品以回调结果里的
<code>payId</code> 为准，不要信任客户端上传的商品 ID；发货对象始终是发来消息的已鉴权玩家。</li>
<li>支付回调里不要调用 <code>cloudEnqueue</code> / <code>cloudFlush</code>；平台会等 <code>fulfill</code> 的写入生效后再完成订单。</li>
<li><code>already_delivered</code> 表示已经发过，不要当成拒单；未完成的订单可以用同一 <code>orderId</code> 再次 <code>doOrder</code> 补发。</li>
</ol>
<h3 id="玩法消息带宽">玩法消息带宽</h3>
<p>线上所有 Room 都同时执行用户和房间两层带宽限制。上行指客户端发给 Room，下行指 Room 发给客户端，
<code>1 KB = 1024 字节</code>。额度包含完整玩法消息帧和协议开销，不只是业务正文。</p>

</div><p>有效人数为 <code>min(当前已连接的去重用户数 + 1, 房间最大人数)</code>。例如最大 5 人的房间，1 人在线时房间按
2 人额度计算，满员时按 5 人计算；每个用户仍受个人额度限制。同一用户的多条连接共享个人额度，
线上传输方式切换或重连不会立即重置额度。广播按实际接收连接数累计，定向发送只计目标连接。</p>
<p>每个范围、每个方向都必须同时满足：<strong>过去 5 秒累计不超过基础速率 × 5 秒，过去 1 秒累计不超过基础速率 ×
2 秒</strong>。例如单用户上行在额度充足时可集中发送 20 KB，但任意 5 秒最多累计 50 KB，不能持续每秒发送
20 KB。统计按 100ms 分桶，窗口边界最多保守延后 100ms；恢复取决于历史用量何时过期，不保证等一秒就恢复。</p>
<p>超限时拒绝相应玩法消息，并报告 <code>ROOM_BANDWIDTH_LIMIT_EXCEEDED</code>。带宽超限本身不关闭 Room，额度恢复后可继续
处理新消息，但已拒绝的消息不会自动补发。可靠信道也不能保证超额消息被接受；关键操作需要业务确认和有界、
幂等的重试，不能立即反复重发。超限通知、进离房确认和迁移通知不占玩法额度。</p>
<p>上表的 <strong>1 MiB / 4 MiB 是 Room 回调向平台提交输出的运行时预算，不是玩家可用网络带宽</strong>；一次广播在运行时
按一条输出计算，实际发送时还要按接收连接累计字节，并同时满足网络限额。单帧未超过 65535 字节也不意味着
当前带宽一定允许发送，分块不能绕过累计限制。</p>
<p>设计同步时，用“编码后单条大小 × 每秒发送次数 × 实际接收连接数”估算最坏输出。优先使用紧凑二进制、
增量同步、合并限频和按队伍或可见范围定向发送；完整快照与重连补发也应纳入预算。</p>
