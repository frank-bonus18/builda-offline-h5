# Dynamic DPR (render resolution cap, controlled by the host App)

> The examples and export configuration in this section focus on Godot Web; HTML5 projects (pixi/phaser) work the same way — just put `mobile-perf.js` in `<head>` before the engine/renderer initializes, and the pixi/phaser `resolution` option should also read the overridden `devicePixelRatio`.

High-DPI phones render the web canvas at 2–3x device pixels, making the GPU shade 4–9x more fragments, which causes heating and frame drops. On weaker or older WebKit it can also exhaust WebGL memory, showing up as lost contexts and failed lighting/shadow rendering.

To address this, put a tiny `mobile-perf.js` in the bundle that overrides `window.devicePixelRatio` before the engine creates its canvas, lowering the render buffer.

Key point: the value is decided by the host App and passed in via the URL parameter `?dpr=`. The web side only executes it and makes no device/OS judgment at all (the browser cannot get the iPhone/iPad model anyway). The App decides based on the device and appends the parameter.

## Usage: the App appends `?dpr=N` to the URL when launching the game

```text
.../index.html?dpr=1     soft / most compatible (old, weak devices)
.../index.html?dpr=2     compromise
.../index.html?dpr=3     sharpest (new devices)
.../index.html?dpr=0     (or omitted) no cap, use the device's native DPR
```

- `?dpr=` can coexist with other parameters (matched by `[?&]dpr=`, position does not matter), e.g. `?builda_token=...&dpr=2`.
- Rule: if `?dpr=N` is present and N>0, cap `devicePixelRatio` at N; otherwise use native.

## Integration: two steps

### 1. Put `mobile-perf.js` in the export directory

File content (`build/web/mobile-perf.js`; make sure it is in the bundle after export):

```js
// Render-resolution cap, driven ONLY by a ?dpr= URL parameter.
// The HOST APP decides the value and appends it when launching the game.
// Must run before the engine sizes its canvas (loaded from <head>).
(function () {
  try {
    var m = (location.search || "").match(/[?&]dpr=(-?[0-9.]+)/)
    if (!m) return;             // no param -> native DPR
    var cap = parseFloat(m[1])
    if (!(cap > 0)) return;     // ?dpr=0 (or invalid) -> explicit no cap
    var real = window.devicePixelRatio || 1
    if (real > cap) {
      Object.defineProperty(window, "devicePixelRatio", {
        configurable: true,
        get: function () { return cap; },
        set: function () {}     // tolerate engine assignments
      })
      console.log("[mobile-perf] DPR " + real + " -> " + cap)
    }
  } catch (e) {}
})()
```

### 2. Load it in the Web export preset's `html/head_include`

It must come before the Godot loader. The Web preset in `export_presets.cfg`:

```ini
html/head_include="<script src=\"mobile-perf.js\"></script><script src=\"builda-sdk.js\"></script>"
```

`mobile-perf.js` must be placed before `builda-sdk.js` / the Godot engine script, because the `devicePixelRatio` override must take effect before the engine creates the WebGL context / sets the canvas size. Changing it after the engine starts is too late; the canvas has already been allocated at native DPR.

## Key points / pitfalls

1. Must run before the engine: it can only run in `<head>`, before the Godot loader. Putting it in GDScript (`_ready`) is already too late; by then the canvas/context has been created at native DPR. So the decision of "which DPR to use" must be made at the earliest JS layer or passed in by the App.
2. Keep the judgment in the host: the browser UA contains no iPhone/iPad model, and 14 vs. 12/13 with the same screen cannot be distinguished, so device tiering can only rely on the App. The web side makes no judgment and only honors `?dpr=`.
3. Export keeps it: Godot export only generates `index.*` and will not overwrite a hand-placed `mobile-perf.js`; but make sure it ends up in the final bundle — the packaging script needs to stage it.
4. Debugging: just add `?dpr=1/2/3/0` to the URL to compare on any machine, no repackaging needed.
